# Durable snapshot reservation: implementation brief

2026-09-13. Draft saved before the independent notice checkout check. No implementation or qualification is authorized by this document.

Add one reservation journal and one exclusive gate for each existing snapshot. The first useful outcome is concrete: a second controller cannot reserve the same snapshot, and a fresh manager cannot forget an interrupted reservation. Keep acquisition, publication, model construction and automatic recovery of unknown processes closed.

Use fresh scratch source files `snapshot_reservations.py` and `reservation_file_port.py`, with narrow revisions of copies of `snapshot_lifecycle.py` and `generated_worker_flow.py`. Keep all prior files unchanged. The first file owns the bounded record grammar, transitions and live reservation objects. The second owns generated-file persistence and an injected exact-handle exclusion/flush port. Its real entry remains closed until the file API protocol has been reviewed. Do not add a database or a generic persistence framework.

Canonical identity must come from trusted containment and retained directory identities, not a caller's normalized string. Bind the registered store's volume/file ID, the snapshot directory's volume/file ID, approved choice/revision and manifest digest. Case and spelling aliases of the same approved directory must resolve to one gate. The gate key excludes manifest and generation: a changed manifest for the same physical slot must collide with the existing reservation, not create another lock. The manifest remains mandatory inside every record. The first version covers existing snapshots only; reserving nonexistent publication slots belongs to the future writer/publisher connection.

Hold the gate from journal inspection through native lifetime and final durable completion. It must exclude other controllers as well as threads, and its handle must never be inherited by the worker. An exclusive CreateFile gate on a fixed contained sidecar is a concrete proposed Windows implementation, reusing the existing handle ownership rules. Exact open/share flags and flush behavior require their own source review before any generated native observation. An in-memory RLock is not cross-process exclusion. A writer must acquire the same gate, require a clean reservation state and the existing native protection checks, then keep exclusion through its entire mutation; this brief does not implement publication or deletion.

Use a bounded append-only journal so a failed write cannot overwrite the previous blocking record. Each frame has a fixed schema/version, sequence, predecessor digest, canonical identity, generation, transition, bounded reason enum and checksum. Reject duplicate fields, unknown versions, sequence gaps, mismatched identities, incomplete frames, checksum failures and trailing bytes. Proposed initial bounds are 4 KiB per frame and 4 MiB per journal; exhaustion blocks new work. Compaction is outside this first implementation. These checks detect inconsistency, not malicious rewriting by an actor with the same filesystem privileges.

Avoid replacement in this first unit: append through the same exclusively retained journal handle, confirm byte counts and flush, then reread the bounded frame through that handle. The persistence port must state its actual Windows implementation before any native run. A successful process-crash test does not establish power-loss durability; directory-entry persistence, the filesystem and storage stack remain limits until explicitly qualified. Never claim atomic rename alone would settle those limits. A missing or damaged journal after restart remains blocked.

The start order is fixed:

1. Acquire the canonical gate and inspect the entire bounded journal. Missing state for an already registered snapshot is unknown and blocked. Initialization is allowed only for a newly generated snapshot with a private creation capability; an arbitrary empty directory does not establish first use.
2. Retain the snapshot read protection. Append RESERVED with generation and manifest, finish all short writes, flush and confirm the same open journal identity before process creation. Failure leaves the local reservation quarantined and creates no worker.
3. Create the owned worker suspended, retaining its exact process/thread/job handles. Record its observed PID and full creation time under the same generation, append WORKER_BOUND and flush before resume. A write failure must stop only that exact owned worker, preserve uncertainty and keep the gate/read protection. Recorded PID or creation time never authorizes a kill, attachment or model operation.
4. Resume only while the exact live reservation token remains current and both persistence acknowledgements succeeded. A concurrent revoke wins publication. No manager-wide state lock may be held across a blocking write/flush; use a pending transition token, perform I/O outside the lock, and validate the token on return. Other entrants see the pending reservation as busy.

Quarantine sets the in-memory phase and revokes admission before attempting I/O. Append QUARANTINED, retaining RESERVED/WORKER_BOUND if append or flush fails. Return persistence success only after the exact operation acknowledges it. Preserve both the original failure and persistence failure; an exception while recording must not free live native buffers or guards. The journal is diagnostic state and exclusion policy, never an executable capability.

Normal completion requires the current live owner's existing exact process wait, empty-job observation, zero active operations and terminal pipe I/O before native handles/read protection can be retired. Append CLEARED only after required teardown confirms success, while still holding the gate; flush before dropping the gate. A failed final persistence step leaves the durable reservation blocking, even if native cleanup succeeded. Quarantined records have a separate reconciliation path, so a late successful join cannot silently change ordinary release semantics.

Startup must classify RESERVED, WORKER_BOUND, QUARANTINED, corrupt, missing and unknown-format state as blocked. Do not recover from a timeout, absent PID, reused PID, wire claim or stored CLEARED field alone. A clean terminal record is only one prerequisite for fresh reservation; canonical gate and current native protection still apply. The first reconciliation operation accepts an opaque observation issued by the retained live owner or a separately trusted observer, bound to the exact generation, canonical identity and process ownership. It cannot accept a deserialized observation. Across a true restart, when that ownership cannot be reconstructed, keep the record quarantined. The current anonymous job cannot be reopened from its old name or number.

A later generated crash observation should retain the exact worker process handle in an observer, crash its controller, observe worker exit and file-guard availability, and start a fresh manager that remains blocked before reconciliation. Holding another job handle could change kill-on-job-close behavior, so the observer must not claim that it both retained the job and tested last-job-handle closure. Exact restart reconciliation, unavailable process identity and lost anonymous-job evidence remain engineering work. No new Ryan ruling is needed to preserve quarantine while those facts are unknown.

The focused implementation tests should cover canonical aliases and changed-manifest collisions; two competing managers; malformed/torn/full journals; every write/flush boundary before create and resume; a late persistence acknowledgement after revoke; stored PID reuse with no process action; quarantine-write failure retaining local ownership; successful live-owner clearing; failed final-clear persistence; and a fresh manager refusing each incomplete state. Use generated bytes and fake exact-handle ports first. Add only the separately reviewed generated controller-crash observation afterward. Reuse the existing lifecycle and generated-flow tests unchanged, with ordinary raw counts and source hashes. No additional proof framework is needed.

Routine engineering choices are the frame bounds, gate namespace and conservative refusal policy. The Windows exclusion/flush implementation and restart reconciliation need technical review and generated qualification, not an invented user approval. Existing Ryan decisions about real assets, conversion, runtime migration and release remain unchanged. This brief grants none of those actions.
