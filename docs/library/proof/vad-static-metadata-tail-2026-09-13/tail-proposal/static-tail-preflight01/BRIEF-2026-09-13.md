# Bounded literal-token tail reporting proposal

The completed run03 inventory remains valid for its recorded static scope.
Its 80-payload final seal was verified unchanged before this new proposal.
The current first-64 identifier sample ends among state-dictionary-looking
tokens; it cannot describe later matching tokens. The separate fixed-loader
proposal still lacks established checkpoint architecture/configuration.

This new reporting instrument will copy the approved compatibility reader
exactly, then add only a last-64 matching-token sample. It uses the existing
STRING_OPS selection and IDENTIFIER regex, with the same 96-character maximum.
The tail retains the last 64 occurrences in opcode order, including repeated
tokens. It is not a list of unique keys, key/value associations or inferred
architecture. Each additional sample comes from an opcode argument already
parsed by the reader; it adds no file read, class resolution or construction.

The existing first-64 unique identifier samples remain unchanged, as do opcode
counts, GLOBAL literals and all other inventory fields. The only output
additions are `identifier_string_tail_samples` and `string_tail_sample_limit`.
All fixed paths, exact-artifact hash checks, format predicates, resource limits,
model prohibitions and the 256-KiB output cap remain unchanged. The tail list
will never retain more than 64 strings or a token longer than 96 characters.

`before/read_checkpoint_inventory.py` preserves the exact executed reader.
`before/prior-final-proof-SHA256.json` is a copy of the existing final seal;
its payload paths refer to that original outer proof, not files duplicated in
this small proposal. `preservation.json` identifies and verifies that intact
proof. No old source, result, assertion, refusal or seal is superseded.

After the reporting edit and exact diff are recorded, a fresh synthetic run
will use `-I -S -B` and compare the approved and new parser outputs on small
in-memory ZIPs and literal pickle byte strings. It will cover more than 64
identifiers, bounded tail order, repeated occurrences, length/regex boundaries,
empty samples, unchanged other fields and unchanged refusals. An exact AST
comparison will permit only the described tail bookkeeping/return fields;
all input reads, acceptance predicates, hash gates and model behavior must
remain equal. Both readers' `inspect` and `main` will be disabled, and the
actual checkpoint open will be prohibited.

The subagent will not run an actual inventory. The root may review one future
exact-hash-bound static read under a fresh label if this instrument qualifies.
It must not overwrite run03 or relabel that completed inventory. Literal
tokens cannot authorize a fixed class, configuration, tensor schema, model
load, conversion or inference. Work stays in this fresh scratch directory
while the root's product tree runs. This brief precedes all reporting edits
and synthetic qualification.
